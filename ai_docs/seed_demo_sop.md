# seed_demo — Developer SOP

## Purpose & business context

`python manage.py seed_demo` builds the local development/demo dataset for the
CDS Business HR platform. It exists so every developer sees a realistic,
populated app: a real org chart, real request/timesheet history, attendance,
notifications, and meaningful review queues — without touching production.

It is **local-development only** and **never runs on container startup**
(compose only auto-runs `migrate`).

## Commands

```bash
python manage.py seed_demo                       # idempotent top-up (no deletes)
python manage.py seed_demo --reset               # wipe demo data + rebuild
python manage.py seed_demo --reset --password 'CDS!Demo2026'
python manage.py seed_demo --scale 50            # +50 bulk employees w/ requests
```

Inside Docker: `docker compose exec backend python manage.py seed_demo --reset`

### Workflows & request types (configuration — preserved on --reset)

- **Manager approval** — single MANAGER step → Annual Leave, Sick Leave,
  Remote Work; also the timesheet workflow.
- **Manager + HR approval** — MANAGER → HR → Equipment Purchase.
- **HR approval** — single HR step → General Request.

### Transactional data (created only where missing → idempotent)

- **Requests**: 8–13 per developer/implementor + 2 General Requests per manager.
  Status mix ~45% APPROVED / ~25% PENDING / ~10% WITHDRAWN / ~8% REJECTED /
  ~7% RETURNED + IN_REVIEW for two-step items parked at the HR step. Some
  RETURNED items are resubmitted and approved, producing full audit chains.
- **Timesheets**: up to 7 weeks per developer/implementor (Monday-keyed
  `week_start`, Sun–Sat business week). Daily entry hours are derived from the
  same user's real attendance (`Sum(worked_duration)`, rounded to 0.25h), so
  timesheet ↔ attendance never contradict. Older weeks mostly APPROVED; last
  week mixed; the current week stays PENDING in the manager queue and ~35% of
  users get no current-week sheet so the "New timesheet" flow stays testable.
- **Attendance**: ~8 weeks back for all 16 users. Work week Sun–Thu
  (Fri/Sat ~3% chance). Check-in 08:30–10:50 Africa/Cairo, check-out
  16:30–19:30 Cairo — stored as UTC. ~16% of days are split into two sessions
  (break). Never seeds today and never leaves an open session, so manual
  Check In/Out testing stays clean.
- **Notifications**: generated by the real `emit()` path during submission and
  every workflow action; ~70% of outcome notifications backdated as read.
  "Awaiting your review" nudges stay unread while the item is actually open,
  and get marked read (80%) just before a review action.
- **Audit entries**: real `audit_record()`/`wfs.act()` output — every request
  and timesheet has a consistent history whose `created_at` matches the
  item's timeline.
- **Attachments**: up to 8 small real files (txt/pdf) on editable requests
  (PENDING without reviewer action, or RETURNED).

## Backdating mechanics

`submitted_at`, `created_at`, `updated_at` are `auto_now*`/`auto_now_add`
fields — the seeder writes each object through the real service functions
(`submit_request`, `wfs.act`, `emit`, `audit_record`) and then moves
timestamps into the past with `queryset.update()` (the only way to override
auto-now fields). Determinism comes from per-user/per-concern RNG streams:
`random.Random(f"{SEED}:{local}:{req|att|ts:{week}}")`.

## --reset: what is deleted vs preserved

**Deleted** (single transaction, ORM only): Attachments (+files on disk and
the `media/attachments/` tree), Requests, Timesheets (+entries), Attendance
sessions, Notifications, Audit entries, all non-superuser Users, Django
sessions, and SimpleJWT blacklist/outstanding tokens.

**Preserved**: migrations, schema, superuser accounts, and all Workflow /
WorkflowStep / RequestType configuration.

## Safety guard

`_assert_local_dev()` runs on every invocation. The command aborts unless the
DB is sqlite, or `DEBUG=True` and the DB host is loopback/docker-internal
(`localhost`, `127.0.0.1`, `::1`, `db`, `postgres`, `10.*`, `172.*`,
`192.168.*`) and the DB name doesn't contain `prod`/`staging`/`stage`.

## Idempotency

Every generated slice is guarded by an existence check (user has requests? —
per-user; attendance present? — per-user; timesheet exists for
(submitter, week_start)? — per-week; attachments exist? — global). Because the
RNG streams are keyed per slice, skipping existing slices doesn't change what
a rerun generates for missing slices.

## Integration points

- Uses `apps.requests.services.submit_request` — real request submission.
- Uses `apps.workflows.services.act` — real transitions (status, current_step,
  current_actor_role, requires_hr_review stay consistent with the snapshot).
- Uses `apps.notifications.services.emit` / `apps.audit.services.record`.

## Test scenarios

- **Happy path**: `seed_demo --reset` → 16 users, ~140 requests, ~86
  timesheets, ~700 sessions, ~415 notifications; all 16 log in with
  `CDS!Demo2026`.
- **Idempotent**: `seed_demo` twice → identical counts.
- **Guard**: run against non-DEBUG/remote DB → CommandError, zero writes.
- **Permission**: HR sees only General Request + Equipment step-2 items;
  managers see only their own reports' items.
- **Edge**: no open attendance, no today/future sessions, WITHDRAWN shows as
  Cancelled in the UI.

## Known limitations / deferred

- HR user has no own requests/timesheets (a self-routed HR-step review would
  be unrealistic).
- Managers' own items are General Requests only — MANAGER-step items would
  never resolve (managers have no manager).
- Check-in/out times are generated in Africa/Cairo and stored in UTC; a
  viewer in another timezone sees them shifted accordingly.
